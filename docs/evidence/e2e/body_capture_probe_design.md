## Question and deliberately narrow scope

For the one original GUI Prepare shift-PDF request in a fresh equivalent isolated
journey, can the real application consume complete bytes, then hand those exact
bytes to a completed browser Save, while Playwright's original response.body()
operation is unavailable or its Request is marked failed?

The experiment repeats C113's pre-PDF clock and historical-report sequence on a
fresh synthetic stack, then studies only SHIFT_PDF. It does not claim C113, XLSX,
order downloads, native Android/viewers, provider execution, or full lifecycle
acceptance. It preserves current-authority validation and an independent executor
403 check for this export. The separate executor denial is never a substitute for
or replay of the master's original authorized response.

## Chosen observation: same-reader tap, no clone or tee

1. Before application initialization, install a closure-scoped fetch observer in
   only the dedicated master page. It forwards the same arguments and this value
   to native fetch once, returning the exact native fetch Promise. It adds a
   fulfillment observer only for a precisely armed export. It never reads request
   bodies, cookies, Authorization, CSRF, credentials, or arbitrary response bodies.
2. Immediately before the real Prepare gesture, arm exactly once using a fresh
   256-bit private capability nonce. The target is fixed at the trusted loopback
   origin, `/api/v1/reports/shift.pdf`, GET, and exactly the canonical start/end
   query generated by the unchanged client, without additional/duplicate fields.
   No nonce is inserted into the URL, headers, request body, evidence, or logs.
3. The observer on the original fetch Promise sees the exact original Response.
   Verify native Response shape, unchanged exact URL, no redirect, status 200,
   protected fixed MIME/disposition/cache/Vary/nosniff/CSP, identity encoding, and
   positive integral Content-Length <= 8 MiB before allocating capture storage.
4. Install an instance-only wrapper on that Response body's getReader. The
   application obtains its original default reader from the native method once.
   Install an instance-only wrapper on that reader's read; return the exact
   original read Promise and preserve each chunk/result object and its contents.
   No BYOB reader, second reader, Response.clone, tee, pipe, transformed stream,
   replacement Response, Blob refetch, retry, cancellation, or extra native read.
5. Attach a non-throwing observer to each original read Promise before returning
   it. Synchronously copy only Uint8Array bytes actually resolved to the client,
   in order, into the bounded capture buffer. A read rejection records only a
   fixed category. An unexpected method/shape or install failure invalidates the
   observation without trying another capture route or altering the client result.
6. Require a single reader, sequential reads, a real done:true result, exact
   declared byte count, and no mismatch/overflow/rejection. Compute SHA-256 from
   the filled, exact-sized buffer without concatenating or slicing a second
   payload-sized JavaScript buffer. Return only a fixed schema, digest, lengths,
   booleans, and allowlisted states across the browser bridge. Never return bytes.
7. The observation is of bytes delivered to the actual client reader. This does
   not independently prove that UI authority remained current or that the client
   accepted those bytes: unchanged application checks plus visible READY and the
   existing real Save/content/auth checks supply those separate observations.

### Perturbation and standards limits

This is an instrumented run, not a passive or uninstrumented reliability test.
Attaching rejection handlers also marks selected promises handled for the host's
unhandled-rejection reporting. The application still receives the same rejected
promises and rejection values, but otherwise unhandledrejection notifications can
be suppressed by observation; host event behavior is not claimed unchanged.
Observer installation, extra Promise reactions and copying take time before the
client's continuations. The digest consumes CPU and browser implementation memory.
This may affect scheduling, timeout races and effective application pull timing.
Returning the same promises avoids deliberately adding an awaited read chain;
it does not eliminate the observer effect. No network backpressure queue is added
because no tee or independent consumer exists, but delayed client pulls can still
change effective backpressure. Record this limitation with every result.

Response.clone was rejected for this first experiment: the Fetch body-clone
algorithm tees the stream and replaces the original body stream; a second branch
can change buffering/backpressure and cancellation behavior. Tee cancellation may
wait for the other branch. A clone alternative would need separate review and a
bounded cancellation design, and would remain diagnostic-only.

Standards checked during design:
- https://fetch.spec.whatwg.org/#concept-body-clone
- https://streams.spec.whatwg.org/#readable-stream-default-tee

## Exact original-request binding

The nonce is a private capability and one-shot local arm, not a new network
identity. Cross-realm correspondence is established by all of these invariants:

- Fresh master context, current verified synthetic master session, main frame only
- Exactly one armed native-fetch invocation for the exact canonical export URL
- Existing API client arguments remain untouched, including same-origin mode and
  credentials, no-store cache, redirect:error, headers, and original abort signal
- Node routing guard arms before Prepare, binds the sole exact Request object
  before dispatch, and aborts/counts a duplicate or unexpected export GET
- response.request() must be that same selected Request object; final response URL
  must match exactly; no redirectedFrom/redirectedTo, service worker, route fulfill,
  response mocking, or response replacement
- Browser tap counts and Node request counts must both equal one; response header
  projections and byte length must agree; no export GET may occur on Save
- The Node completion observer remains bound to this exact Request object before
  and after the unchanged original CDP body call
- Wrong/missing/replayed nonce, wrong page/frame, method, query, period or response,
  duplicate request or unarmed request makes the experiment INVALID_BINDING

No timing-only, 'latest request', URL-only fallback, or second successful response
can repair a failed binding. When browser and Node observations cannot be joined
unambiguously, the result is inconclusive, never evidence of successful transfer.

## Bounded memory, time, cleanup

- Capture-owned payload storage: one Uint8Array of declared length, 1..8 MiB;
  never allocate for missing/invalid/zero/oversized Content-Length
- Validate a chunk's type/size and cumulative length before copying; overflow
  invalidates the capture immediately. No unbounded chunk list or byte bridge
- Digest receives the exact complete buffer directly. Browser crypto internals may
  make a bounded native copy; do not claim total browser memory is only 8 MiB
- Explicit experiment-owned payload ceilings: capture 8 MiB in browser, possible
  crypto native copy <= 8 MiB, original CDP response <= 8 MiB, saved file <= 8 MiB;
  retain at most one PDF experiment at a time. Engine/network internals are outside
  this accounting and no absolute Chromium-RSS cap is claimed
- Arm-to-EOF budget 20 seconds, digest budget 5 seconds, Node observation watchdog
  25 seconds, original CDP body budget unchanged at 20 seconds; Save completes
  within the existing READY TTL. Whole test remains bounded at 240 seconds
- Timeout is terminal. Late read/digest continuations check the terminal generation
  and cannot resurrect success or write bytes. Raw rejection reasons are discarded
- Restore only own installed properties, drop nonce/Response/reader references,
  clear timers and listeners, zero/drop the owned capture buffer on completion,
  invalidation, timeout, navigation/context closure, and explicit disposal
- Never await reader.cancel or lock release as cleanup; the application owns them.
  Instrumentation does not consume, abort, unlock, or otherwise rescue the stream
- Node finally disposes the tap and closes the dedicated contexts even if page
  cleanup is unavailable. Owned-buffer zeroing is not a secure-erasure guarantee
  for browser internal copies or saved synthetic files
- Saved synthetic PDF, expected-value file, raw Playwright report/stdout/stderr and
  browser artifacts remain in a 0700 private temporary directory. The launcher
  removes that directory on every outcome and publishes only the validated fixed
  safe-evidence projection; no PDF or raw browser artifact is uploaded
- Playwright response.body() may allocate before its returned length is checked.
  That operation relies on the unchanged server export cap; its check is not an
  independent Chromium-memory limit. This does not alter the 8 MiB tap-owned cap

## Preserve the original oracle and inspect actual Save

The unchanged `c113_downloads.cjs::boundedResponseBody` is called exactly once for
this original response, with its unchanged bodyFailure and Request observations.
Its result is permanently recorded as OK with actual length/hash, or FAILED with
an allowlisted failure category. A failure is never overwritten by tap/saved data.
No existing C113 file, evidence, gate predicate, or failure record is edited.

In this separate diagnostic only, after recording the original CDP outcome, the
runner may continue to the existing explicit Save gesture if UI is actually READY
and tap binding is valid. Require no early download, exact suggested filename,
completed download, fresh regular nonsymlink saved file, 1..8 MiB size, no new
export request, and inspect actual file bytes with the unchanged independent
C113 PDF inspector and exact canonical expected values.

When CDP bytes exist, require their exact byte equality to saved bytes, plus all
three hashes equal. When CDP bytes are unavailable, literal CDP-to-saved equality
is UNAVAILABLE, never PASS. Separately compare tap complete-byte digest/length to
saved-file digest/length and inspect its actual content. The latter is independent
diagnostic evidence, not a replacement for C113's required original equality.

Verify two independent secure sessions and current /me principal/scope, executor
UI absence and server 403 on the exact export, no unauthorized mutation, and
unchanged business DB snapshot. Auth/clock changes retain C113's explicit bounds.
The original baseline failed run remains red even if this experiment is useful.

## Comparative criteria (no C113 PASS output)

All rows carry `scope=INSTRUMENTED_DIAGNOSTIC_ONLY`,
`c113_acceptance=NOT_ESTABLISHED`, exact source hashes, and baseline failed run ID.
Execution can end `DIAGNOSTIC_COMPLETE`, `INCONCLUSIVE`, or `BLOCKED`. There is no
PASS field or acceptance receipt that an existing C113 gate could accept.

| CDP original | Client tap | Actual Save/inspection/auth | Interpretation |
| --- | --- | --- | --- |
| FAILED/unavailable | complete, exact length | valid and hash-equal | Instrumented client delivery and saved integrity succeeded while original CDP retrieval failed; suggests observation/transport-report divergence for this run only |
| OK | complete, hashes equal | valid, literal CDP equality | Instrumented agreement; historical intermittent failure not explained or repaired |
| any | truncated/read error/timeout | absent or invalid | Transfer or consumption failure observed, or instrumentation interference; retain exact categories, do not assign root cause |
| OK | mismatch or invalid binding | any | Probe integrity/association failed; no conclusion about CDP or product |
| FAILED | complete | saved hash/content/auth failure | Original body failure plus a distinct saved-file/auth failure; not a capture-only explanation |
| any | missing/unsupported observation | any | Inconclusive or blocked; no alternate capture route |

A requestfailed event is retained independently even if all saved-file checks
succeed; do not redefine it as requestfinished. A single experiment cannot establish
intermittent reliability, prove Chromium root cause, or validate production fixes.
