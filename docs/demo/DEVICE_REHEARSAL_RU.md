Исходники описания: `f3b3ffd00d8bb59e55d539e2321196bf18c30d7d`.
**Статус всех физических шагов: NOT_RUN.** Это future acceptance-процедура,
не запись произошедшего демо. В этом SHA нет собранного frontend/login пути.

## Перед стартом

1. Интегратор даёт exact SHA, проверенный HTTPS-origin, фактические команды
   запуска/seed и версию синтетического набора. Не угадывать URL и команды
2. Два реальных Android: отдельный мастер и исполнитель; третий экран менеджера
   только при готовом read-only отчёте. Зафиксировать модель/OS/browser, режим
   браузер/PWA, foreground/background/locked и тип сети. Эмуляция viewport отдельно
3. Демо-аккаунты только изолированные; пароли/PIN/куки не показывать, не записывать
   в ledger и не открывать без разрешения. Роли/области доступа подтверждены
4. Человек разрешает камеру/уведомления для тестового origin. Разрешение не
   подразумевается из назначения сценария. Реальные отправки только в отдельно
   разрешённый тестовый канал/получателю; эта инструкция их не разрешает
5. Для live создать свежую задачу штатным API с допустимым дедлайном. Historical
   seed/export не отправлять как live POST. Предварительно подготовленные состояния
   и управляемое demo-время подписать; production-время не изменять
6. Фото синтетическое/безопасное: без лиц, бейджей, документов, EXIF/GPS и данных
   предприятия. Не заявлять, что текстовая замена имён обезличивает изображение
7. Оператор проверяет реальную готовность каждого шага заранее. Непроверенная
   функция остаётся NOT_RUN; нет доступа/настройки — BLOCKED с точной причиной

## Семиминутный маршрут

| 0:50–1:30 | Исполнитель получает, принимает и начинает | Независимый сеанс, committed status/version и время появления у мастера. Проверку locked-screen delivery вынести в отдельную запись |
| 1:30–2:10 | Пауза с причиной → продолжение | Причина, история, отсутствие потери состояния/дублирования; двух активных задач не сводить к одному ложному workload |
| 2:10–3:10 | Внести работы, шифр, материалы, фото и отправить | Реальные bytes upload, подтверждённая привязка к попытке, время загрузки и условия сети, persistence после повторного чтения |
| 3:10–4:00 | Проверка результата → решение мастера | Mode/reasons/evidence, отсутствие оценки отдельно от pending/error, human score отдельно; модель не закрывает наряд |

| 4:50–5:40 | Подготовленная просрочка / уведомление | Объявить подготовку/время, показать job и физическую доставку отдельно. Без разрешённого канала — пропуск с NOT_RUN/BLOCKED |

Это cue sheet, а не требование уместить загрузку или таймаут любой длительности
в заданный интервал. Если фактическое время больше, назвать его и перейти к
проверенному резерву. Не ускорять запись без маркировки и не исключать ошибки
из измерений. Полные негативные drills ниже выполняются вне 7 минут.

## Измерения: заранее согласовать границы

- Выдача: t0 — открыта форма создания; t1 — подтверждён сохранённый наряд.
  Если официальный benchmark использует иную границу, зафиксировать её отдельно.
  Цели ≤60 секунд / ≤6 нажатий — не результат. Записать все действия, включение
  клавиатуры/выбор справочников/камеры и долю предварительного заполнения;
  не смешивать методики между устройствами
- Обновление у мастера: от подтверждённого изменения исполнителем до видимого
  актуального состояния мастера. Внутренняя server latency не заменяет end-to-end.
  Цель ≤5 секунд; назвать способ синхронизации часов/общую видеозапись и погрешность
- Фото: t0 перед отправкой bytes, t1 после серверного подтверждения; размер до/после
  сжатия, сеть, ошибки/повторы отдельно. Цель ≤10 секунд; preview не конец загрузки
- Push: реальное время провайдера и время появления на конкретном устройстве;
  channel, foreground/background/locked, разрешения, наличие звука/вибрации.
  Provider receipt или `sent` в БД без телефона — другой уровень доказательства
- Для каждой серии указать n и все результаты, не только лучший. p50/p95 давать
  только для фактически собранной выборки с описанной методикой. Экономию не выводить
  из одного демо; произвольную оценку качества/готовности не строить

## Негативные drills вне тайминга

Каждый — отдельный evidence ID, точный SHA, ожидаемый и наблюдаемый результат.

1. Потеря ответа **после commit**: создать неопределённый результат на управляемом
   тестовом стенде, затем повторить тот же запрос. Проверить один созданный наряд,
   один набор ожидаемых событий и один эффект команды, актуальную версию. Offline до отправки этого не доказывает
2. Двойное нажатие, stale version/409, два мастера: UI не скрывает конфликт и
   не стирает форму; ни один успех не рисуется до подтверждения
3. Чужой order/photo/report, role/session смена: сервер запрещает доступ;
   отсутствие кнопки недостаточно. Старые данные и pending outbox не переходят
   под другую учётную запись
4. Сеть пропала, reconnect/back/forward: явный статус, штатное восстановление,
   новый snapshot. Не сбрасывать локально неподтверждённую операцию молча
5. Фото с неверным содержимым/типом: серверная ошибка, а не только UI-фильтр;
   неполный результат нельзя закрыть. Синтетический `file_valid` не byte validation
6. Model timeout/невалидный ответ: только согласованный тестовый способ, без
   новых платных запросов; отметить mock/synthetic отдельно от реального провайдера
7. Push denied/locked screen/restart: UI правдиво показывает ограничение,
   повтор scheduler не создаёт дубли. Проверка planner не означает проверку доставки
8. Устаревшая AI-попытка после переназначения не меняет новый наряд

## Запись результата

В ledger добавить отдельные строки `browser_assembled`, `real_database`,
`physical_device`, `push_delivery`, `real_model` по реально пройденным слоям.
Нужны SHA, UTC timestamp, проверяющий, устройство/браузер/сеть, command или
точные действия, PASS/FAIL/NOT_RUN/BLOCKED и безопасный артефакт. Не включать
credentials, session IDs, лица, внутренние runtime paths или необработанные логи.
Видео/скриншот должен показывать тот же кандидат. Выполненный один шаг не
повышает автоматически статус всего сценария.
