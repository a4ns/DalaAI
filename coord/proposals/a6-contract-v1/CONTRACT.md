# v1 thin-slice semantics

Status: 1.0.0-proposal.2, PROPOSED, not frozen. A0/human A acceptance pending; B0 and C0 consumer approval pending. The `/api/v1` choice and all field names must be accepted before shared-client generation. Preparation has no published contract SHA or application commit.

## Surface, ownership and explicit limits

The 12 operations cover login/logout/me, reference dictionaries, order list/read/create/commands, per-order events, historical submission read, staged upload and protected image read. A0/A6 own the wire proposal; A1 implements order rules, A2 auth and uploads, A3 jobs/realtime, A4 AI, A5 runtime, B4 generated client, C1 synthetic fixtures and C5 independent end-to-end acceptance.

No reports, analytics, offline queue, notification-subscription API, WebSocket transport or deployment management are specified here. Required case reports and device notifications remain subsequent work, not declared unnecessary or complete. Infrastructure `/healthz` and `/readyz` belong to A5 outside this domain OpenAPI. Dictionary responses are scoped to caller permissions; admin does not gain implicit master rights.

OpenAPI syntax follows the official [OpenAPI 3.1.0 specification](https://spec.openapis.org/oas/v3.1.0.html). The artifact deliberately targets 3.1.0 for a proposed common toolchain; it makes no claim that this is the latest version. JSON Schema 2020-12 fixtures and the typed FastAPI OpenAPI document parser are run offline. A dedicated full OpenAPI specification validator and generated-client compatibility remain unrun.

## Authorization and session contract

- `Principal.user_id` is the authenticated employee UUID; `active` is account status, `on_shift` is scheduling status. Client actor/role fields are rejected
- Master: create and review/write within allowed sections. Executor: current assignment AND section membership; only executor actions. Manager: scoped read-only. Admin: no implicit order execution or production-review privilege
- A brigade assignment always includes one responsible executor. Validate that person's section, brigade membership and eligibility; do not infer collective acceptance from brigade_id
- All protected routes, image reads and every receipt replay recheck current permissions. Previously assigned executors cannot retrieve old receipts after losing access. Unknown object returns 404; an existing unauthorized object returns 403 without contents
- `__Host-naryadai_session`: opaque session handle, Secure, HttpOnly, SameSite=Strict, Path=/, no Domain. A2 handles hashing, revocation, expiration and active-account checks on real time
- Authenticated unsafe HTTP requires exact configured Origin and session-bound X-CSRF-Token. `/auth/login` requires exact Origin and JSON, generic errors and real-clock rate limits. No wildcard credential CORS and no token in URLs
- `/me` returns a session-bound CSRF token so reloads recover safely; A2 proposes a synchronizer token held in restricted server-side session storage, separate from the opaque session handle, and constant-time comparison. Never log it; it is not a bearer authenticator
- Login/logout are session operations, not domain-receipt commands. Staged uploads and all order writes use operation IDs. Logout clears browser identity/cache; queued work must never silently run as a new user

## Mutations, receipt replay and versioning

For a newly issued order, due_at must be strictly after domain_now at processing time. A0 accepted this as a proposed product rule, not an official case requirement. Historical seed loading preserves historical deadlines; it does not use live issue validation. If a draft deadline expires while in transit, return a clear validation error and preserve inputs, without silently moving the deadline.

Create has `expected_version=0` and `action=create`; other commands require integer expected_version>=1. This integer is the whole order aggregate version, not assignment_revision or an HTTP ETag. UUID operation_id is generated once by the client for one user intent, retained across unknown-result retries, and not regenerated by a transport retry.

The receipt key is `(actor_id, operation_id)` across ALL mutating domain routes. Its canonical hash includes HTTP method, normalized route/resource ID, action, expected_version and validated payload. Reject duplicate JSON keys, non-finite numbers, unknown fields and noncanonical ambiguous input. Normalize UUIDs and timestamps and decimal quantities consistently before SHA-256 hashing. The exact canonicalization implementation and its golden vectors are a pre-integration test gate. For multipart upload include the SHA-256 of original received file bytes and typed form metadata; the returned photo SHA-256 describes sanitized stored bytes.

After authentication and current resource authorization, a same-hash committed receipt returns the original HTTP status/body, including the OLD snapshot/version and original event IDs. Do not rerun stale expected_version or transition validation. This protects lost-response retries. Fetch latest snapshot when the user wants current state. Different hash gives 409 OPERATION_ID_REUSED, including reuse against another resource. For create, authorize submitted section/master capability and the receipt's created resource scope before returning saved content. For uploads, recheck owner/order scope; replay does not extend expiration.

New command effects, events, jobs and finalized receipt commit together. Reserve the unique receipt in the same transaction and use row lock plus CAS/version increment. Do not implement a read-check without locking/CAS. A losing unique insertion waits, then reads the winner's committed receipt. On rollback, the reservation disappears. Failed commands produce no successful receipt. After 409 the UI preserves form values, loads current state and obtains a fresh operation ID only for the user's newly resolved intent.

Order.version starts at 1. Each user command increments once; submit produces two ordered events (`done`, then `ai_review`) but only one version increment and no externally committed `done` snapshot. An asynchronous non-stale assessment can increment the current order version and append an assessment event without changing status; this may legitimately conflict with a concurrently prepared review. A stale job appends only to its old attempt and never changes current version, status or current notification jobs. Event sequence and version are different: multiple events may share one version.

## State transition boundary

| Actor/action | Allowed source | Destination | Required guard |
|---|---|---|---|
| master/create | absent | issued | eligible assignment, scoped valid dictionaries |
| executor/queue | issued | queued | assigned + section |
| executor/accept | issued, queued | accepted | assigned + section |
| executor/reject | issued | rejected | nonblank reason |
| executor/start | accepted, rework | in_progress | assigned + section |
| executor/pause | in_progress | paused | nonblank reason |
| executor/resume | paused | in_progress | assigned + section |
| executor/submit | in_progress | done → ai_review | immutable new attempt and safe attached files |
| master/review(close) | ai_review | closed | current attempt + complete hard gates + reason |
| master/review(rework) | ai_review | rework | current attempt + reason |
| master/reassign | any nonterminal | issued | new assignment + reason; revision increment |
| master/cancel | any nonterminal | cancelled | reason; invalidate scheduled jobs |
| master/change_priority | any nonterminal | unchanged | reason; reschedule affected jobs |

`closed` and `cancelled` are terminal. No reopen and no AI auto-close. A reassign command requires a materially new assignment (responsible executor and/or brigade); do not silently recycle an identical assignment to clear rejection. Deadline editing is not part of this slice. Priority changes keep due_at but increment scheduling_revision because emergency acceptance thresholds change. Reassignment increments assignment_revision and scheduling_revision; cancellation increments scheduling_revision. Old attempts/events remain visible to currently authorized readers. Reasons and previous/new assignment/priority metadata are preserved in append-only events.

## Submission, review and photo rules

Required wire fields distinguish missing/unknown data from empty lists. Nonblank work_description is mandatory. `work_code_id=null` or no after-photo for unplanned work creates an explicit incomplete submission with server-calculated missing_evidence. Planned work does not require after-photo. Unknown work code/material IDs, duplicate material IDs, nonpositive quantity, excessive numeric precision, wrong MIME, foreign/expired/already-bound photos or malformed work text fail validation. The incomplete result can be analyzed and returned for rework; it cannot be closed even with a high model/human score.

Submissions never update in place. New attempt numbers are allocated under order lock within each assignment revision. After human rework, the executor restarts and submits a new attempt. Human review references the current submission_id; check its order, assignment revision and hard gates again under lock. A review reason is always mandatory, including an override of an AI recommendation/score. Manager/admin privileges cannot substitute for a master decision. Human manual review is permitted when AI is pending or failed, but mandatory evidence remains required. `final_score=null` means unscored, not zero.

Photos: every stage request includes section_id. The server checks that section against current principal scope; after-photo requests must also match the DB-loaded order section. Persist the verified section on the photo and return it as StagedPhoto.section_id. A master stages before-photos with no nonexistent order ID. After-photo staging is restricted to the assigned executor and requires order_id and current assignment_revision. Before uses neither of those fields. Stage is private, owner-scoped and expires after 24 REAL hours. Accept at most 5 before and 5 after per attempt; proposed 8 MiB/file and 20-megapixel decode cap. These caps await A2/B0 approval, and do not prove the <=10s mobile target. Decode/reencode, strip EXIF/GPS, assign safe storage names and validate actual image bytes. Never fetch arbitrary remote URLs. EXIF/client taken_at is not trusted capture time.

Attach stages atomically with create or submit. The A1 staged-photo port receives the destination_section_id from validated create.section_id or the DB-loaded order.section_id. The A2 adapter loads the stored staged section and requires exact destination equality, even if the same owner is authorized in both sections. Cross-section stage/attachment returns 403 FORBIDDEN; missing or malformed section_id returns 422 VALIDATION_FAILED. The SQL candidate also binds an attached photo to the same order section using a composite foreign key. Failed create/submit does not consume or orphan the user's successful stage; timeout replay preserves the original relation. A stage is single-use. Attached photos are not TTL garbage-collection candidates. Binding after-photos checks assignment revision again. Image reads use object authorization and private/no-store caching, with no public bucket URL.

## Clocks, events and jobs

Persist timestamps in UTC, render user-facing time as UTC+5. The supported RFC3339 timestamp profile requires a timezone and real calendar date; leap-second notation is not accepted by this Python-backed slice. Real clock governs session/TTL/security/worker lease/network retry. Domain clock governs due dates, work timestamps and reminder thresholds; visible demo time never alters session or retry expiry.

`is_overdue = domain_now > due_at` for issued/queued/accepted/rejected/in_progress/paused/rework. It is false in done/ai_review/closed/cancelled. Submission.done_late is calculated at submission from original due_at and is immutable; do not rewrite deadlines to improve historical statistics. Rework resumes deadline monitoring against the existing due_at.

Per-order events have UUID dedupe identity and monotonic order-local sequence. Clients drain pages (`has_more`) and advance only to returned next_after_sequence, then reconcile a current authorized snapshot. A recommended <=2s poll is an implementation setting to be measured against the <=5s case target; it is not evidence of meeting it. Network interruption retains an unknown result rather than displaying false success. A live polling badge is not a phone push.

An internal DeliveryJob is deduped by `(order_id, assignment_revision, scheduling_revision, kind, recipient_id, channel, bucket)`. `bucket` distinguishes one-shot initial/reminder, a submission/review attempt ID, or a configured repeat window. It is NEVER NULL. Jobs are durable in the command transaction; scheduler insertion uses the same unique key. Domain due_at crossings use <=, not equality. Proposed case thresholds: 30 minutes before deadline, 10 minutes unaccepted normal/high, 3 minutes unaccepted emergency. Repeats and manager escalation thresholds must be separately accepted, not invented as case requirements.

Before dispatch, recheck actual status, current responsible recipient, assignment/scheduling revision and whether the threshold is still applicable. Provider network calls occur outside DB transactions. Store real-clock attempts, lease/retry time, provider receipt and sanitized error code. Restart workers reclaim expired leases. At-least-once transport plus idempotent jobs is the attainable boundary; provider timeout may have sent a message. `provider_accepted` is not proof of phone receipt, vibration or sound. Adapter choice, permissions and real-device evidence belong to A3 and the device operator. No real employee contacts are included.

## Failure mapping and client behavior

- 400 INVALID_REQUEST: broken/ambiguous request; fix input
- 401 UNAUTHENTICATED: session absent/revoked/expired; stop sending and isolate previous user's cached data
- 403 FORBIDDEN: role/scope/CSRF/origin rejected; no object content
- 404 NOT_FOUND: unknown resource
- 409 VERSION_CONFLICT / TRANSITION_CONFLICT / STALE_ASSIGNMENT: preserve form, fetch state, explicit resolution
- 409 OPERATION_ID_REUSED: programming/user-intent conflict; do not silently change ID and resend
- 409 INCOMPLETE_SUBMISSION: human close blocked by mandatory gate; show missing evidence
- 422 VALIDATION_FAILED / PHOTO_EXPIRED: correct specific safe field errors; reupload only with user awareness
- 413 PAYLOAD_TOO_LARGE; 415 UNSUPPORTED_MEDIA_TYPE: retain draft; compress/select valid image
- 429 RATE_LIMITED / 503 TEMPORARILY_UNAVAILABLE: honor real-second Retry-After. If commit outcome was unknown, resend EXACT same operation_id/body

Error request_id is server generated. current_version and field details are included only after authorization. Avoid PINs, credentials, names, raw prompts and image contents in logs or error details. Successful transport/schema tests cannot prove authorization, atomicity, physical image quality or phone delivery.

```
python scripts/build_contract.py
python scripts/validate_contract.py
```

Exact directly used validation versions are declared in requirements-validation.txt. The validator registers an explicit standard-library date-time checker, asserts required format availability and executes positive/negative probes; it never assumes optional jsonschema format extras are installed. A5 owns integration into root dependencies/lockfiles. Build regeneration is deterministic. The validation output's executed_at records the actual check time and includes all unrun stages.
